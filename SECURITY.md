(carried from the 2026-10-13 scan, not re-checked)

Suppose a sizing change makes all-body words 18px of ink instead of the baseline 15px (a 20% oversize), next to a 13px long-word x-height. At the shipped value, 1.21, the metric scores 0.8739. That is below the gate floor of 0.9036 (baseline 0.9536 on all three seeds, `REGRESSION_TOLERANCE = 0.05`), so the push is blocked. In acceptEdits or auto mode the Edit tool makes that change without a prompt. The tripwire `test_metric_is_independent_of_sizing_constants` passes even at 1.45 (`good` = 0.9195). The first quick test to fail is `test_shouted_short_word_scores_low`, at 1.30. Larger shifts also require editing `tests/quick/test_xheight_normalization.py`, which is unprotected too. cd7ee60 closed the accidental path, because tuning `ZONE_HEIGHT_RATIOS` in `config.py` no longer moves the metric.   Evidence: `visual.py:561-567` holds the constant and its comment, and `:597` uses it. `reforge/config.py:161-162` reads `PRIMARY_METRICS = ["x_height_consistency"]`. The `.claude/settings.json` ask rules cover only `quality_baseline.json`, `regression_gate.py` and the two `--update-*` flags. The numbers above come from probes that patched the module attribute in memory, with no file edits. One ran the real `check_x_height_consistency` on synthetic word blocks. Ask rules still do not cover writes from a Python subprocess (see the carried NOTE below).

[NOTE] .claude/settings.json:4-7 -- The evaluator ask rules cover only built-in edits to two files plus two flag substrings. They do not enforce most of what CLAUDE.md:102 lists as requiring human approval, and ask beats the broad allow rules in `settings.local.json` only for commands that match an ask pattern. Confidence: high. (carried from the 2026-10-13 scan, not re-checked)
  Attack vector: The adversary is the project's own coding agent, either reward-hacking toward a green gate or steered by injected text. (1) Subprocess writes. `.venv/bin/python -c "..."` that rewrites `tests/medium/quality_baseline.json` or `reforge/evaluate/regression_gate.py` matches the allow rule `Bash(.venv/bin/python:*)` (`.claude/settings.local.json:42`) and no ask rule. Claude Code applies Edit rules to its built-in file tools, to recognized file commands such as `sed` and `tee`, and to redirection targets. Its permission docs say they do not apply to "arbitrary subprocesses that read or write files indirectly, like a Python or Node script that opens files itself". In auto mode the outcome then rests on the allow rule or the classifier, not on a human prompt. (2) Gate-defining files with no rule, which auto and acceptEdits modes edit without a prompt: `reforge/config.py:161` (`PRIMARY_METRICS`) and `:189` (`QUALITY_CONTINUOUS_WEIGHTS`), `tests/medium/test_quality_regression.py:45,56,85,296` (`SSIM_THRESHOLD`, `TEST_WORDS`, `REGRESSION_TOLERANCE`, `strict=True`), `tests/medium/conftest.py:10-18` (flag defaults), `tests/medium/reference_output.png`, and the metric code in `reforge/evaluate/visual.py`. Setting `PRIMARY_METRICS = []` or `REGRESSION_TOLERANCE = 1.0` disables the primary-metric check and leaves every protected file untouched.
  Evidence: The ask list is at `.claude/settings.json:4-7`. CLAUDE.md:102 names `PRIMARY_METRICS`, gate thresholds, the gate's word list, `quality_baseline.json`, `reference_output.png` and `QUALITY_CONTINUOUS_WEIGHTS` as human-approval items and says the settings file "enforces part of this".
  Remediation: Move the gate-defining constants (primary metrics, tolerance, SSIM threshold, word list) into the protected `regression_gate.py` or one dedicated gate file. Add ask rules for `tests/medium/test_quality_regression.py`, `tests/medium/conftest.py`, `tests/medium/reference_output.png` and `reforge/evaluate/visual.py`. For enforcement that also covers subprocesses, enable Claude Code sandboxing with write denial on those paths, or replace the interpreter-wide allows (`Bash(.venv/bin/python:*)`, `Bash(.venv/bin/python3:*)`, `Bash(python -c *)`, `Bash(bash:*)`) with specific commands.

[NOTE] reforge/model/generator.py:1170 -- Words from user text that fail OCR are appended, with a timestamp, to `reforge/data/hard_words.json`. That file is tracked in this public repository, and the 2026-10-13 audit push routes more user tokens into it. Confidence: medium. (carried from the 2026-10-13 scan, not re-checked)
  Attack vector: A reader of the public repository. When `reforge.py --text ...` renders a private note, any single-chunk word whose OCR stays below 0.4 after two retries reaches `_record_hard_word_candidate` (generator.py:1168-1170, 1233-1239). `add_candidate` (`reforge/data/words.py:65-89`) then writes it to `_HARD_WORDS_PATH` (words.py:18). There is no opt-out. Since the audit push, generator.py:1004-1017 sends every token with trailing punctuation through the retry loop, so "Smith." is now recorded as "Smith". The removed `_generate_punctuated_word` path never recorded anything.
  Evidence: generator.py:1004-1017, 1168-1170 and 1233-1239; words.py:18 and 65-89; `git ls-files reforge/data/hard_words.json` lists the file.
  Remediation: Record auto-collected candidates in a gitignored location (`experiments/output/` is already ignored) and let the triage CLI promote them from there into the tracked curated list.
